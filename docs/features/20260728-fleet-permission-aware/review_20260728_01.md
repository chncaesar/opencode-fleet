# Review 01: fleet-permission-aware

Date: 20260728
Branch: feature/fleet-permission-aware

## Summary

实现整体质量良好：数据模型正确（permissionCache 独立于 statusCache）、`permission.asked` 追加语义正确、idle/session.idle 两个事件路径均清理了 permissionCache、encodeURIComponent 编码到位、reply 枚举在 handler 层有运行时二次校验。所有单元测试（35 个）通过，构建无报错。发现 3 个 Major 问题、5 个 Minor 问题，无 Critical 问题。

问题汇总：Critical 0 / Major 3 / Minor 5，共 8 项。

## Issues

### Critical

无。

### Major

- [M1] `replyPermission` HTTP 失败后 `removePendingPermission` 未调用，这是正确的——但反过来，如果 `removePendingPermission` 在 `replyPermission` 成功后、返回 `ok()` 之前抛出（当前实现中不会，因为它是纯 Map 操作），缓存将残留。更严重的是：**DESIGN.md §5 明确要求 tools.test.ts 覆盖 "HTTP 调用失败" 场景**（"HTTP 调用返回非 204：返回 isError=true，附带 HTTP 状态码"），但 tests/tools.test.ts 中没有一个测试用例覆盖 `replyPermission` 抛出 `NodeError` 的错误路径。`makeStatusCtx` 中已准备了 `replyPermissionResult?: Error` 的 mock 基础设施，但从未被任何测试实际使用。错误路径覆盖缺失。 — `tests/tools.test.ts:66`

- [M2] E2E 测试完全未覆盖本 feature 的两个新能力。DESIGN.md §5（E2E 测试策略）明确要求：  
  1. 注入 pending permissions 后调用 `fleet_get_session_status`，验证输出包含 permission 段落  
  2. 注入后调用 `fleet_reply_permission` 成功（mock HTTP 204），验证 permissionCache 被清理  

  `tests/e2e/tools.e2e.ts` 中无任何 `fleet_reply_permission` 测试，也无注入状态后的 `fleet_get_session_status` permission 段落验证。`injectPermissionForTesting` 已公开（可在 E2E 中使用），但 `.env.e2e.example` 也未按 DESIGN.md 要求添加可选场景的 `skipIf` 环境变量注释。 — `tests/e2e/tools.e2e.ts`

- [M3] `handleReplyPermission` 的成功消息写死了"Session is now unblocked"，但实际上 reply="reject" 时 slave session 并不是"unblocked"继续执行，而是工具调用收到拒绝错误，session 可能仍然 busy 或出错。这个措辞对 reply="reject" 场景具有误导性，与 DESIGN.md §2.6 正常返回格式描述（reply="once" 才是 unblocked）不一致，可能导致 master agent 误判 session 状态。 — `src/tools.ts:1037`

### Minor

- [m1] `src/node.ts:597` 和 `src/tools.ts:1045` 之后各有一个多余的空行（连续两个空行），不符合文件内其他区域的单空行风格。 — `src/node.ts:597–599`，`src/tools.ts:1045–1047`

- [m2] tests/node.test.ts 未测试 `session.idle`（deprecated 事件类型）触发 permissionCache 清理的路径。`applyEvent` 中已实现该分支（`src/node.ts:473`），但对应的 applyEventForTesting 测试仅覆盖了 `session.status` 路径。DESIGN.md §2.3 要求两种事件均触发清理。 — `tests/node.test.ts`

- [m3] `handleGetSessionStatus` 在 busy 分支获取 `pending` 后，只有 `pending.length > 0` 时才追加 permission 段落。这是正确的向后兼容实现。但 `pending` 变量的声明位置（嵌套在 `if (status.type === "busy")` 块内，位于第 963 行）与其他 handler 的本地变量提前声明风格稍有不同，建议加注释说明为何只在 busy 分支调用，防止后续维护时误移到外层。 — `src/tools.ts:963`

- [m4] `replyPermission` 直接使用了 `fetch` 而非 `this.request()`，绕过了 `request()` 中的统一错误处理和响应文本提取逻辑。虽然 204 响应没有 body（`request()` 的 text/JSON 解析对其行为不确定），但此处应保持一致，或在注释中说明为何不能复用 `this.request()`（因为它对非 ok 状态抛异常，而 204 本身 `res.ok === true`，所以实际上可以用 `this.request<void>()`）。 — `src/node.ts:584`

- [m5] `injectPermissionForTesting` 和 `applyEventForTesting` 方法使用 `@internal` JSDoc 标注，但它们是 `OpenCodeNode` 的公共方法（`public`）。TypeScript 中没有 `@internal` 的运行时效果；若希望阻止外部调用者在 IDE 中发现这些方法，应考虑使用 `/** @internal */` + `_` 前缀约定，或将其移入一个测试辅助模块（如 `src/node.test-utils.ts`）并仅在测试中导入。当前做法在生产 dist 中暴露了测试专用方法。 — `src/node.ts:529`，`src/node.ts:540`
